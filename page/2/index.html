Javs设计模式

Posted on 2024-04-12 Edited on 2024-09-08 In 设计模式

设计原则

  • 开闭原则：类对扩展开放，对修改关闭
  • 里氏替换原则：类扩展时，子类对象替换父类对象，不改变调用方法预期结果
  • 接口隔离原则：客户端不应该强迫接口实现不适用的方法

使用场景

  • 复用设计模式
    • 适配器模式
  • 避免资源浪费，节省内存空间
    • 享元模式 FlyWeight
    • 代理模式 Proxy
  • 管理状态
    • 观察者模式 Observer
    • 备忘录模式 Memento
    • 状态模式 State
  • 通过一个类和其他类打交道
    • 门面模式 Facade
    • 中介者模式 Mediator

设计模式分类

![设计模式学习路线 by 程序员鱼皮](https://hyle-1325187152.cos.ap-guangzhou.myqcloud.com/imgs/设计模式学习路线 by 程序员鱼皮.png)

创建型设计模式：

这些模式涉及对象的创建机制，试图以适合情况的方式创建对象。它们可以被分类为：

  1. 单例模式：确保一个类只有一个实例，并提供对该实例的全局访问点。
  2. 建造者模式：将复杂对象的构建与其表示分离，允许相同的构建过程创建不同的表示。
  3. 工厂方法模式：定义一个用于创建对象的接口，但允许子类修改将被创建的对象的类型。
  4. 抽象工厂模式：提供一个创建一系列相关或依赖对象的接口，而无需指定它们的具体类。
  5. 原型模式：通过复制现有对象（称为原型）来创建新对象。

结构型设计模式：

这些模式涉及对象组合或结构。它们描述了如何组合类和对象以形成更大的结构。结构设计模式包括：

  1. 适配器模式：允许具有不兼容接口的对象协作。

  2. 桥接模式：将抽象与其实现分离，使两者能够独立变化。

  3. 组合模式：将对象组合成树形结构以表示整体-部分层次结构。组合模式使客户端能够统一地处理单个对象和对象组合。

  4. 装饰者模式：动态地向对象添加额外的责任。装饰器为扩展功能提供了一种灵活的替代方法，而不需要子类化。

  5. 外观模式：为子系统中的一组接口提供一个统一的接口。外观定义了一个更高级别的接口，使子系统更容易使用。

  6. 享元模式：使用共享来有效地支持大量细粒度的对象。

  7. 代理模式：为另一个对象提供一个代理或占位符，以控制对它的访问。

行为型设计模式：

这些模式涉及算法和对象之间责任的分配。它们不仅描述了对象或类的模式，还描述了它们之间通信的模式。行为设计模式包括：

  1. 责任链模式：通过给多个对象一个处理请求的机会，避免了请求的发送者与其接收者之间的耦合。

  2. 命令模式：将一个请求封装为一个对象，从而允许使用队列、请求和操作对客户端进行参数化。

  3. 解释器模式：提供一种评估语言语法或表达式的方式。

  4. 迭代器模式：提供一种访问聚合对象元素的顺序方法，而不暴露其底层表示。

  5. 中介者模式：定义了一个对象来封装一组对象的交互方式。中介者通过不让对象直接相互引用来促进松耦合，并允许它们的交互独立变化。

  6. 备忘录模式：捕获并外部化对象的内部状态，以便稍后可以将对象恢复到此状态。

  7. 观察者模式：定义了对象之间的一对多依赖关系，使得当一个对象的状态发生变化时，所有依赖于它的对象都会被自动通知并更新。

  8. 状态模式：当对象的内部状态发生变化时，允许对象改变其行为。对象将表现出似乎改变了类的行为。

  9. 策略模式：定义一系列算法，将每个算法都封装起来，并使它们可以互换。策略允许算法独立于使用它的客户端而变化。

  10. 模板方法模式：在超类中定义算法的框架，但允许子类在不改变其结构的情况下重写特定步骤的算法。

  11. 访问者模式：表示要对对象结构执行的操作。访问者允许定义一个新的操作，而无需改变它所作用的元素的类。

创建型模式

单例模式

作用

确保类只有一个实例，并提供全局访问点。

实现方式

  • 实例字段和构造方法是私有的

  • 饿汉式（Eager Initialization）：在类加载时就创建实例，在程序运行期间始终存在。线程安全，但可能会造成内存空间浪费。

  • 懒汉式（Lazy Initialization）：在第一次使用时创建实例。线程不安全，需要考虑多线程环境下的同步问题。

  • 双重检测锁（Double-Checked Locking）：在懒汉式的基础上进行改进，减少了同步的开销。适用于 Java 5 及以上版本。

  • 静态内部类：利用类加载机制，保证线程安全且延迟加载。当 Holder 类加载时，静态内部类 InnerClass 不会被加载进内存，直到调用 getInstance()方法时才会加载，同时保证了线程安全性。

    ==以上的方法都是不安全的，可以通过反射、反编译破坏单例模式==

  • 枚举：利用枚举类型的特性，保证了线程安全和防止反序列化破坏单例。

MySQL 事务

1. 什么是事务？什么是数据库事务？SS

  • 事务是一组 SQL 操作，被视为一个单独的工作单元，要么全部成功提交，要么全部失败回滚。

  • 数据库事务可以保证多个对数据库的操作（也就是 SQL 语句）构成⼀ 个逻辑上的整体。构成这个逻辑上的整体的这些数据库操作遵循：要么全部执⾏ 成功,要么全部不执⾏ 。关系型数据库（例如： MySQL 、 SQL Server 、 Orac le 等）事务都有 ACID 特性。

2. ACID 特性？SS

  • 保证了事务的持久性、原⼦性、隔离性之后，⼀致性才能得到保障。也就是说 A、I、D 是⼿段，C 是⽬的

3. 并发事务带来了哪些问题? SS

  • 脏读（Dirty read）：读取了未提交的数据
  • 丢失修改（Lost to modify）：一个事务的修改覆盖了另一个事务
  • 不可重复读 （Unrepeatable read）：重复读了同一数据前后不一致
  • 幻读（Phantom read）：读某个表多了一行数据

4. SQL 标准定义了哪些事务隔离级别?SS

  • READ-UNCOMMITTED(读取未提交)：同时读，同时写，同时读写
  • READ-COMMITTED(读取已提交)：同时写，同时读写
  • REPEATABLE-READ(可重复读)：同时读写
  • SERIALIZABLE(可串⾏化)。

6. 什么是 MVCC？有什么⽤？原理了解么？SS

RC（Read Committed，读提交）和 RR（Repeatable Read，可重复读）这两个隔离级别的实现都离不开 MVCC。

MySQL 锁

锁的分类 SS

  1. 表级锁和⾏级锁了解吗？有什么区别？

    表级锁(table-level locking)⼀锁就锁整张表。⾏级锁的粒度更⼩，仅对相关的记录上锁即可（对⼀⾏或者多⾏记录加锁）

  2. ⾏级锁的使⽤有什么注意事项？

    InnoDB 的⾏锁是针对索引字段加的锁，表级锁是针对⾮索引字段加的 锁。当我们执⾏ UPDATE、 DELETE 语句时，如果 WHERE 条 件中字段没有命 中索引或者索引失效的话，就会导致扫描全表对表中的所有记录进⾏加锁。

  3. 意向锁有什么作⽤？

    快速判断是否可以对某个表使⽤表锁。意向锁是表级锁，共有两种。并且，意向锁之间是互相兼容的。

4. 索引分类

主键索引和二级索引

  • 数据表的主键列使⽤的就是主键索引。

  • ⼆级索引⼜称为辅助索引，是因 为⼆级索引的叶⼦节点存储的数据是主键列。也就是说，通过⼆级索引，可以定位主键的位置。唯⼀索引，普通索引，前缀索引等索引属于⼆级索引。

聚集索引和非聚集索引

  • 聚集索引：索引结构和数据放一起。主键索引属于聚集索引。一个表只有一个聚集索引（数据存一份），一般是主键列。

  • 回表：查询某个非聚集索引得到主键，通过主键的聚集索引返回完整的记录。

    主键索引不需要回表。

最左匹配原则

在 MySQL 建⽴联合索引时会遵守最左前缀匹配原则，即最左优先，在 检索数据时从联合索引的最左边开始匹配。

6.索引失效的情况

  1. 模糊匹配%，like 查询以“%”开头；

  2. or 语句前后没有同时使用索引；

  3. where 语句对索引列进行了运算

  4. 联合索引中不是使用第一列索引；

    • （联合索引(column1, column2)，查询条件有 column2，没有 column1，不会走索引）

  5. 在索引列上使用“is null”或“is not null”操作；

  6. 在索引字段上使用“not”，“！=”等。

7.建立索引的使用场景

在最频繁使用的、用以缩小查询范围的字段，需要排列的字段上建立索引。
不宜：

  1. 查询中很少涉及或者重复值比较多的字段；
  2. 频繁更新的字段。
  3. 一些特殊的数据类型，比如文本字段（text）等。

MySQL 日志

  1. MySQL 中常⻅的⽇志有哪些？

错误⽇志（error log）、⼆进制⽇志（binary log）、⼀般查询⽇志 （general query log）、慢查询⽇志（slow query log） 、事务⽇志(redo log 和 undo log) ……。

mysql 三大日志——binlog、redolog、undolog

答：

redolog:是 InnoDB 存储引擎层的日志，物理日志。又称重做日志文件，用于记录事务操作的变化，记录的是数据修改后的值，不管事务是否提交都会记录下来。
Binlog：是 Mysql Server 层面的，又称为归档日志，属于逻辑日志，以二进制的形式记录的，用于记录数据库执行的写入性操作（不包括查询）信息。

Undolog：主要记录了数据的逻辑变化，保存了事务发生之前的数据的一个版本，这样在发生错误时，就能回滚到事务之前的数据状态。

  1. 慢查询⽇志有什么⽤？

    慢查询⽇志记录了执⾏时间超过 long_query_time （默认是 10s） 的所有查询，在我们解决 SQL 慢查询（SQL 执⾏时间过⻓）问题的时候经常会⽤ 到。

3. binlog 主要记录了什么？有什么⽤？SS

MySQL binlog(binary log 即⼆进制⽇志⽂件) 主要记录了 MySQL 数据 库中数据的所有变化(数据库执⾏的所有 DDL 和 DML 语句)。

4. redo log 如何保证事务的持久性？SS

redo log 主要做的事情就是记录⻚的修改，⽐如某个⻚⾯某个偏移量处 修改了⼏个字节的值以及具体被修改的内容是什么。在事务提交时，我们会将 redo log 按照刷盘策略刷到磁盘上去，这样即使 MySQL 宕机了，重启之后也能 恢复未能写⼊磁盘的数据，从⽽保证事务的持久性。

5. ⻚修改之后为什么不直接刷盘呢？

性能⾮常差！InnoDB ⻚的⼤⼩⼀般为 16KB，⽽⻚⼜是磁盘和内存交 互的基本单位。这就导致即使我们只修改了⻚中的⼏个字节数据，⼀次刷盘操作 也需要将 16KB ⼤⼩的⻚整个都刷新到磁盘中。⽽且，这些修改的⻚可能并不相 邻，也就是说这还是随机 IO。

贪吃蛇对战系统项目总结

Posted on 2024-03-25 In SpringBoot项目

实现用户注册登录功能

  • 注册：判断数据非空和是否合理，初始化，调用接口向数据库添加数据

  • 登录：使用Spring Security的方法 将账号，密码加密成JwtToken，如果登录成功向前端返回JwtToken,登录失败Spring Security会自动处理。

  • 获取个人信息：用户发送请求时，还会发送JwtToken，使用Spring Sercurity的函数解析token获取用户个人信息。

  • 使用 Spring Security 配置JWT认证机制，使用JWT来进行用户认证，后端实现JWT的token的生成与验证，根据token获取用户信息，最后实现登录和开发的业务。

游戏动画的实现：

游戏动画在前端实现，通过js的requestAnimationFrame函数在浏览器实现动画，实现一个游戏对象递归调用该函数，在该函数调用前实现一些游戏的逻辑，游戏的逻辑涉及随机地图的生成，蛇的移动，地图和蛇的位置的数据存储在数组中，之后使用绘画标签canvas将地图和蛇渲染在页面上。

游戏同步：

使用websocket实现前后端实时相互通信，使用WebSocketServer这个类来维护websocket连接。前端用户通过websocket向后端传输操作数据。后端要将游戏开始产生的地图数据以及游戏双方操作后两条蛇的坐标数据通过webserver实时通信到两个客户端，然后客户端将数据渲染到浏览器。

游戏逻辑的实现：

  • 随机地图的生成：

使用一个二维数组来存储地图信息，把空地设置为0，把障碍设置为1，地图的四周设置为1，每次生成障碍时生成两个随机数表示行号和列号，把它设置为1,要保证地图是公平的，使用障碍坐标中心对称后的坐标也设置为1，要保证两条蛇有交互性，则保证地图是连通的，可以使用bfs算法来判断地图是否连通。

  • 蛇移动的逻辑：

使用一个动态数组来存储蛇身的坐标，使用dx，dy两个数组来表示蛇上下左右移动的偏移量，由于蛇每次移动所有坐标都要变换的逻辑过于复杂，我们可以将它理解成头和尾在移动，每次蛇移动时，在动态数组前面插入一个蛇头的新坐标即可，然后判断当前回合蛇是否增长，如果不增长，则将蛇尾坐标在数组中删除，如果增长，则保持不变。从而实现了蛇移动的逻辑。

  • 游戏流程：

为了保证游戏不会阻塞其他的玩家的匹配，游戏等业务，游戏整个逻辑需要使用多线程来实现。

在两名玩家匹配成功后，会启动游戏线程，初始化会生成地图数据和两条蛇的初始坐标。

使用一个status变量来表示游戏的状态，一个loser变量来记录胜负。

游戏循环n个回合，n是游戏最大的回合数，每个回合，先判断游戏是否结束，如果结束，将游戏结果返回给前端，否则等待两个玩家的输入，5s则视为超时，判负处理，游戏状态改为结束；若两名玩家都有输入，判断操作是否合理，操作不合理判负，游戏状态改成结束，操作合理则会存储蛇移动的数据并进入下一回合。

匹配系统的实现：

匹配的逻辑额外使用另一个微服务来实现。

前端通过websocket向后端传输匹配者的信息，后端再把信息传输给匹配系统的微服务，匹配系统把匹配成功后的消息在传输给后端，后端再调用游戏的逻辑开始一局游戏，后端和匹配系统之间的数据传输通过RestTemplate来实现。

  • 匹配流程：

    为了保证匹配不会阻塞其他玩家的匹配，匹配功能需要使用多线程来实现。

    使用一个列表来存储所有玩家，称做匹配池。每次后端发来一个请求时，如果请求匹配，把玩家的数据加入到匹配池中；如果请求取消匹配时，在匹配池删去该玩家。

    每个玩家会有一个分数变量，我们根据分数差距来匹配，随着匹配时间的增长，每增长一秒，允许玩家分数差距增加10。

    写一个死循环，每次线程sleep 1s，然后扫描匹配池所有玩家，将玩家匹配时间的变量加1，然后循环每一个玩家，去和其他玩家判断是否符合匹配条件，符合条件，将两个玩家的数据返回给后端，退出循环，否则进入下一次循环。

我的Bot的实现：

实现Bot数据的CRUD接口，Bot数据主要有id，标题，代码等。

执行Bot代码：

执行Bot代码产生蛇的下一步操作通过另一个微服务来实现。前端匹配时发了一个bot_id表示通过bot操作，后端在执行游戏流程时，不会从前端等待用户输入，而是向Bot微服务发送一个请求。

  • Bot执行代码的流程：

维护一个存储 Bot 对象的队列 bots，后端发来请求时，往队列加入一个bot对象，使用一个consumer类来消费bot对象，获取bot的代码，使用反射来动态编译代码，最后利用反射获取编译后的Bot实例，调用它的nextMove获取蛇下一步移动方向，最后把数据返回给后端。

排行榜和录像功能：

排行榜：根据用户的分数来进行排行，后端实现列表查询接口，包含分页查询的逻辑；

录像功能：每一次游戏会将地图数据，两条蛇的移动数据存成字符串到数据库，从数据库获取数据传到前端并模拟一遍即可。

SpringBoot分层

Posted on 2023-03-25 Edited on 2024-09-08 In SpringBoot

应用分层

  • Controller 层：主要是对访问控制进行转发，各类基本参数校验，或者不复用的业务简单处理等。

  • Service 层：相对具体的业务逻辑服务层。

  • Manager 层：通用业务处理层，它有如下特征：

    1） 对第三方平台封装的层，预处理返回结果及转化异常信息，适配上层接口。

    2） 对 Service 层通用能力的下沉，如缓存方案、中间件通用处理。

    3） 与 DAO 层交互，对多个 DAO 的组合复用。

  • DAO 层：数据访问层（数据持久化），与底层 MySQL、Oracle、Hbase、OB 等进行数据交互。

【参考】分层领域模型规约：

  • DO（Data Object）：此对象与数据库表结构一一对应，通过 DAO 层向上传输数据源对象。
  • DTO（Data Transfer Object）：数据传输对象，Service 或 Manager 向外传输的对象。
  • BO（Business Object）：业务对象，可以由 Service 层输出的封装业务逻辑的对象。
  • Query：数据查询对象，各层接收上层的查询请求。注意超过 2 个参数的查询封装，禁止使用 Map 类 来传输。
  • VO（View Object）：显示层对象，通常是 Web 向模板渲染引擎层传输的对象。

git commit -m "提交说明" 提交所有文件

时空机穿梭

  • 要随时掌握工作区的状态，使用git status命令。

  • 如果git status告诉你有文件被修改过，用git diff <file>可以查看修改内容。

版本库回退

  • HEAD指向的版本就是当前版本，因此，Git允许我们在版本的历史之间穿梭，使用命令git reset --hard <commit_id>。

  • 穿梭前，用git log可以查看提交历史，以便确定要回退到哪个版本。

  • 要重返未来，用git reflog查看命令历史，以便确定要回到未来的哪个版本。

    Git必须知道当前版本是哪个版本，在Git中，用HEAD表示当前版本，也就是最新的提交1094adb...（注意我的提交ID和你的肯定不一样），上一个版本就是HEAD^，上上一个版本就是HEAD^^，当然往上100个版本写100个^比较容易数不过来，所以写成HEAD~100。

工作区和暂存区

工作区：电脑里能看到的目录

版本库(repository)：工作区的一个隐藏目录.git是git的版本库。

Git的版本库里存了很多东西，其中最重要的就是称为stage（或者叫index）的暂存区，还有Git为我们自动创建的第一个分支master，以及指向master的一个指针叫HEAD。

前面讲了我们把文件往Git版本库里添加的时候，是分两步执行的：

第一步是用git add把文件添加进去，实际上就是把文件修改添加到暂存区；

第二步是用git commit提交更改，实际上就是把暂存区的所有内容提交到当前分支。

可以简单理解为，需要 ==提交的文件修改通通放到暂存区，然后，一次性提交暂存区的所有修改== 。

管理修改

git管理的是修改而不是文件，每次修改，如果不用git add到暂存区，那就不会加入到git commit中，即修改不会提交到本地仓库。

如果修改文件后无法提交到本地仓库，需要检查将修改后的文件是不是没有git add加入到暂存区。

撤销修改

场景1：当你改乱了工作区某个文件的内容，想直接丢弃工作区的修改时，用命令git checkout -- <file>。（checkout 检验更新）

场景2：当你不但改乱了工作区某个文件的内容，还添加到了暂存区时，想丢弃修改，分两步，第一步用命令git reset HEAD <file>，就回到了场景1，第二步按场景1操作。

场景3：已经提交了不合适的修改到版本库时，想要撤销本次提交，参考版本回退一节，不过前提是没有推送到远程库。

删除文件

命令git rm用于删除一个文件。如果一个文件已经被提交到版本库，那么你永远不用担心误删，但是要小心，你只能恢复文件到最新版本，你会丢失最近一次提交后你修改的内容。

一种情况是确实要从版本库中删除该文件，那就用命令git rm删掉，并且git commit

另一种情况是删错了，因为版本库里还有呢，所以可以很轻松地把误删的文件恢复到最新版本：

==git checkout其实是用版本库里的版本替换工作区的版本==，无论工作区是修改还是删除，都可以“一键还原”

远程仓库

添加远程库

要关联一个远程库，使用命令git remote add origin git@<server-name:path/repo-name.git>；

git remote add origin git@github.com:hyle777/git_learn

关联一个远程库时必须给远程库指定一个名字，origin是默认习惯命名；

关联后，使用命令git push -u origin master第一次推送master分支的所有内容；

此后，每次本地提交后，只要有必要，就可以使用命令git push origin master推送最新修改；

分布式版本系统的最大好处之一是在本地工作完全不需要考虑远程库的存在，也就是有没有联网都可以正常工作，而SVN在没有联网的时候是拒绝干活的！当有网络的时候，再把本地提交推送一下就完成了同步，真是太方便了！

补充：

列出所有远程仓库信息：git remote -v

在本地仓库删除远程仓库(解除关联)：git remote rm origin

仓库地址可以用http协议(添加关联)：git remote add origin https://github.com/hyle777/git_learn

从远程仓库克隆

要克隆一个仓库，首先必须知道仓库的地址，然后使用git clone命令克隆。

Git支持多种协议，包括https，但ssh协议速度最快。

git clone git@github.com:hyle777.github.io

GitHub给出的地址不止一个，还可以用https://github.com/hyle777/hyle777.github.io这样的地址。

分支管理

创建和合并分支

每次提交，Git都把它们串成一条时间线，这条时间线就是一个分支。截止到目前，只有一条时间线，在Git里，这个分支叫主分支，即master分支(github中主分支为main)。HEAD严格来说不是指向提交，而是指向master，master才是指向提交的，所以，HEAD指向的就是当前分支。

git merge命令用于合并指定分支到当前分支。合并后，再查看readme.txt的内容，就可以看到，和dev分支的最新提交是完全一样的。注意到上面的Fast-forward信息，Git告诉我们，这次合并是“快进模式”，也就是直接把master指向dev的当前提交，所以合并速度非常快。当然，也不是每次合并都能Fast-forward，我们后面会讲其他方式的合并。

因为创建、合并和删除分支非常快，所以Git鼓励你使用分支完成某个任务，合并后再删掉分支，这和直接在master分支上工作效果是一样的，但过程更安全。

合并完成后，就可以放心地删除dev分支了：

Git鼓励大量使用分支：

查看分支：git branch（当前分支前面会标一个*号）

创建分支：git branch <name>

切换分支：git checkout <name>或者git switch <name>

创建+切换分支：git checkout -b <name>或者git switch -c <name>

合并某分支到当前分支：git merge <name>

删除分支：git branch -d <name>

解决冲突

当Git无法自动合并分支时，就必须首先解决冲突。解决冲突后，再提交，合并完成。

解决冲突就是把Git合并失败的文件手动编辑为我们希望的内容，再提交。

用git log --graph命令可以看到分支合并图。

分支管理策略

Git分支十分强大，在团队开发中应该充分应用。

合并分支时，加上--no-ff参数就可以用普通模式合并，合并后的历史有分支，能看出来曾经做过合并，而fast forward合并就看不出来曾经做过合并。

分支策略

在实际开发中，我们应该按照几个基本原则进行分支管理：

首先，master分支应该是非常稳定的，也就是仅用来发布新版本，平时不能在上面干活；

那在哪干活呢？干活都在dev分支上，也就是说，dev分支是不稳定的，到某个时候，比如1.0版本发布时，再把dev分支合并到master上，在master分支发布1.0版本；

你和你的小伙伴们每个人都在dev分支上干活，每个人都有自己的分支，时不时地往dev分支上合并就可以了。

多人协作

当你从远程仓库克隆时，实际上Git自动把本地的master分支和远程的master分支对应起来了，并且，远程仓库的默认名称是origin。

在本地仓库创建dev分支，将工作区的文件提交到dev分支，再推送到远程仓库的dev分支。
